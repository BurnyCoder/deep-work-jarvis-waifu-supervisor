# GPT-6 Luna migration verification

13 October 2026 | Deep Work | Windows 11 | Europe/Berlin

Repository: BurnyCoder/deep-work-jarvis-waifu-supervisor. Baseline: `a78a575`
on `master`; implementation branch: `feat/gpt-6-luna`.

## Question and hypothesis

Can the three existing GPT-5.6 Luna workloads migrate to `gpt-6-luna` while
retaining their Responses API contracts, reasoning settings, and image detail?
The hypothesis was that changing the model identifiers would suffice. OpenAI's
current model page documents image input, structured outputs, and both `medium`
and `xhigh` reasoning. Its image-sizing table did not explicitly list GPT-6
Luna, so successful live requests were required rather than assuming exact
preprocessing behavior from another model's documentation.

## Method and design decisions

Change the three configuration defaults and corresponding environment example;
update the same three model variables in the ignored local `.env`. Preserve
repository `medium` defaults, local `xhigh` overrides, prompts, output schemas,
`original` productivity detail, `low` agent detail, and `gpt-4o-mini-tts` with
the existing voice. Retain OpenAI Python 2.44.0 and the existing lockfile: the
installed client accepts string model IDs and already supports the request
shapes. Reuse production collaborators and existing tests instead of adding a
second API implementation or a new runtime abstraction.

This is one compatibility experiment with automated and live phases. No
controlled old/new accuracy, cost, or latency comparison was performed. The
current chat supplied scope and authorization; repository history, official
documentation, source, tests, local logs, saved responses, and capture inspection
supplied the evidence below.

## Automated results

The existing configuration assertions were updated before implementation.
`uv run pytest tests/test_config.py -q` then produced the expected red result:
1 failed, 6 passed, because the old default was still `gpt-5.6-luna`. After the
three default changes, the focused configuration, main wiring, analyzer, and
feedback suite passed all 44 tests in 8.27 seconds. The full suite passed all
251 tests in 5.98 seconds, and `uv lock --check` passed without a dependency
change. The first focused command named nonexistent `test_messages.py`; file
discovery identified `test_feedback.py`, and the corrected command succeeded.
This was a test-invocation correction, not a product defect.

## Live results

Smoke: `uv run python main.py --smoke` completed with exit code 0. Two monitor
captures and a successful webcam frame formed the stitched image. The
single-capture request returned a valid productivity verdict with HTTP 200,
`model=gpt-6-luna`, `reasoning.effort=xhigh`, and `detail=original`. Its first
observation used the required no-chronological-comparison wording. Speech was
queued, but no Speech API response arrived within smoke's 60-second wait.

Rolling comparison: the exact bounded Python snippet in the verification guide
was executed after smoke exited. Two direct monitor ticks in one unchanged
session returned accepted verdicts. The second request contained the two saved
captures in chronological order, the `COMPARISON (2/5)` header, and `original`
detail for both images. Both inspected composites were 960 by 1896 pixels with
the expected monitor and webcam labels. The first longer speech check received
HTTP 200 about 114 seconds after queueing; its playback call returned before the
next capture. The second Speech API response arrived in about 0.65 seconds,
and the queue drained. There were no ERROR records in either run log. Playback
return and queue completion were observed; audible quality was not independently
measured.

Agent-watch: the existing checker accepted the latest capture with `low` detail
and returned a valid `AgentActivityVerdict` through the same new model. Text:
the existing message generator returned nonempty good-luck feedback through
`gpt-6-luna`. All five successful Responses exchanges (smoke, two rolling
captures, watcher, text) persisted full response objects with status `completed`,
matching request/response model and `xhigh` reasoning, and no response error.
Stored vision requests retained capture paths and detail values without base64
image duplication.

## Findings and limitations

The API/schema compatibility hypothesis passed for all three workloads,
including both image-detail settings. This does not establish a general image
sizing guarantee or an accuracy improvement. Manual inspection found an active
Codex elapsed-time status in the image, while the low-detail watcher reported
idle. That missed activity is a concrete accuracy limitation; the requested
low-detail setting and watcher prompt were preserved. The rolling verdict's
reported changed-file count matched the visible captures, but this small,
uncontrolled sample is not a productivity benchmark.

The slow first speech response explains why the original smoke command could
not establish playback completion. The verification snippet uses a bounded
180-second wait and checks unfinished queue work; production speech behavior is
unchanged. Direct monitor ticks credit the configured five-minute intervals even
when invoked sooner, so the reported ten-minute streak is test accounting, not
measured elapsed work. No enforcer loop, app-kill sweep, real hosts modification,
browser flow, or normal five-minute cadence was exercised in this experiment.

## Review and conclusion

One bounded review covered the changed defaults, independent overrides, request
compatibility, privacy, test coverage, maintainability, logging, and documented
claims. No new runtime path, schema, dependency, or prompt was introduced.
Credential and runtime directories remain ignored. Documentation distinguishes
successful model requests from measured accuracy and speech timing. The model
upgrade is compatible with the exercised contracts, subject to the observed
watcher accuracy and speech latency limitations.
